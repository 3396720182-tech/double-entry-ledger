# 方法说明：落地对账怎么做、为什么这样定门禁

## 1. 要解决的问题

「半落地」：设计文档写得清清楚楚，代码只落了一半，而且看起来像完成了。典型形态（回放里每种都真实出现过，`examples/demo/` 里各有一个虚构的样本）：

| 形态 | 样子 | 谁能抓 |
|---|---|---|
| 入口没接 | 能力实现了，但文档要求的那个入口没调用它 | 正向：实现会话自认未落地 |
| 决策改了、原文没冲销 | 后来的 spec 换了做法，ADR 还写着旧做法；旧做法的读侧分支成了死代码 | 正向：凭证声明「已取代」，取代依据不在来源文档里 |
| 挪位后漏一路 | 登记点从被调函数挪到了调用方，有一条调用路径没跟上 | 正向只给线索（机械驳回 → 复核员顺着查到） |
| 有实现、有单测、零调用 | 校验函数写好了、有单测，入口从没调用 | 反向扫描 |
| 立了规矩没接 | 注释里约定「所有接口都要挂」的工具函数，没有一个调用点 | 反向扫描 |

共同的根因：**没有一个机制回答「这条决定做完了没」**。信息往往存在，只是散在自由文本里，没法机械查询，等于不存在。

## 2. 记账结构

```
设计文档 ──规划会话（只看文档）──▶ 借方：一条代码层承诺一笔，带接线约束
                                        │
代码 ──────实现会话（看代码）──────▶ 凭证：定义 / 生产落点 / 测试 | 自认未落地 | 已取代(依据)
                                        │
                         landing.py reconcile：机械核验（形式，不判语义）
                                        │
            ┌───────────── 门禁 ─────────┴──────────┐
     阻断：没凭证 / 自认未落地 / 自述偏差 /    复核：机械驳回 / 没测试
           取代了但原文没冲销                     （人或独立复核员逐条看）
                                        │
代码 ──────landing.py orphans────▶ 反向：有定义、生产零引用（贷方无借方）
```

和运行时账本（`double-entry-ledger`）是同一套思想：**模型只声明，代码记账、核对，人复核干预项；没查 ≠ 通过。**
区别在时间尺度：运行时账本核对的是一次工具调用有没有产生效果；落地账本核对的是一条决定有没有落到代码里，跨越很多会话。

## 3. 门禁为什么只拦这几类（数据）

回放对象：一个闭源的中型 TypeScript 全栈 monorepo，回放点是一次人工审计之前的提交，审计在那一版里找到了 5 处半落地（参与实验的子代理都看不到审计结论）。详见仓库 `experiments/e3-landing-replay/REPORT.md`。

机械试算（265 笔代码层借方）：入账 113、入账无测试 74、驳回 44、自认未落地 30、已取代 4。对 78 笔没入账的项，3 个独立复核子代理逐条看代码裁定：

| 机器结论 | 笔数 | 复核为真 | 精度 | 门禁 |
|---|---|---|---|---|
| 驳回（REJECTED） | 44 | 2 | 约 5% | 复核，不阻断 |
| 自认未落地（UNLANDED） | 30 | 29 | 97% | 阻断 |
| 已取代（SUPERSEDED，全部是原文没冲销） | 4 | 4 | 100% | 阻断 |

- 驳回的 42 条误报：规则太死 27（类方法、解构、接口成员不认作定义；只跟一层包装；字面量经常量间接引用；`.map(fn)` 式引用），文档名和代码名漂移 14，日志文案 1。
- 已入账随机抽 25 笔，22 笔确实落地，3 笔有缺口（全部 low）；其中 2 笔的凭证 note 里**已经自述了偏差**，机器照样放行 → 本工具新增 `deviations` 字段，自述偏差直接阻断。
- 用阻断三类（自认未落地、自述偏差、取代未冲销，外加没凭证）在回放点上共 34 笔，复核确认 33 笔为真。
- 修好之后的版本上，grep 核验器**仍然驳回**了其中两处已修复的承诺（窗口和多层包装问题）——要是把机械驳回当硬门禁，修好了也过不去。

所以：**高精度的信号来自实现方对自己的陈述，低精度的来自 grep。** 门禁拦前者，后者进清单。本工具在原回放脚本上做了改进：多层包装且按函数体截取、更多定义写法、注释和字符串不算调用、import 行不算调用、scope 只按路径段匹配、写入字面量要以键或赋值的形式出现、取代依据必须指向写明「已取代」的那一行、输入类型严格校验、符号链接不越界。这些改动有的消误报，有的堵假通过（一轮对抗审查复现过的 13 种假通过都有回归用例），但**没有在原数据上重新测精度**，复核仍然必要。

## 4. 已知的脆弱点

1. **能抓到「入口没接」，靠的是实现会话诚实。** 借方如果只写到「函数存在」（`call` 没有 `scope_hint` / `must_include`），一张拿别处调用冒充的对抗凭证就能被机器入账（回放里实测成功；`examples/demo/adversarial/` 复现了这一点）。对策：借方强制带接线约束（`lint` 会提示），实现会话的立场写进提示词（「凭证会被机械核验并由复核员复查」）。
2. **机械驳回不阻断，意味着蓄意造假的凭证只会进复核清单。** 门禁防的是诚实实现方的遗漏和沉默，不是对抗。要防对抗，复核清单必须真的有人或独立复核员看；或者用 `--strict`，代价是误报也会阻断。
3. **借方只能对写进账的东西。** 承诺只活在代码注释、迭代计划或人脑里，就进不了借方——回放里 5 处有 2 处是这样漏掉的，靠反向扫描补上。
4. **反向扫描只看符号级。** 「某个参数取值在生产里从没走到」这类分支级死代码看不到。
5. **测试是否真跑过，工具不知道。** 由调用方用 `--tests` 告知；回放里历史快照跑不了测试（要数据库），这一项全部记为「没查」。
6. **运行时事实不在本账。** 「某个操作执行了多少次、留下了多少条记录」这类计数只有生产数据能回答，应作为独立的一项对账。
7. **静态扫描有上限。** 动态调用（`obj[name]()`、反射、按字符串注册）、依赖注入、多层包装和事件总线这类跨模块的间接调用、写在配置里的接线（路由表、插件清单），扫描都可能看不到；反过来，**有调用点也不等于运行时一定会执行**（特性开关、走不到的分支）。所以本工具的定位是**找出高风险的半落地、交给人或独立 agent 审查，而不是证明代码正确、替代代码审查**。以后换成 AST 或调用图，目的也是减少复核清单里的误报，不是让机器判定取代复核。详见仓库 `docs/architecture.md` §7、§8。

## 5. 接进 OpenSpec / SDD

| 节点 | 做什么 |
|---|---|
| proposal / spec / tasks.md 定稿 | 规划会话从本次 change 的文档开借方，`lint` 通过后和 change 一起提交（`openspec/changes/<id>/debits.json`） |
| 实现 | 实现会话收尾时交凭证（`vouchers.json`），写清自认未落地和偏差 |
| archive 之前 | `reconcile` + `orphans`。阻断项必须处理：落地、或在来源文档里冲销（写明被什么取代）、或由人决定延期并记录。复核项由人签收 |
| archive | 把门禁输出（`--json`）和 debits/vouchers 的哈希写进 archive 记录，作为审计锚点 |

回放里的时间轴：在一次 change 归档的那个提交上跑门禁，「自认未落地 / 取代未冲销」两类就会拦下这次归档，比后来的人工审计早 24 天。

也可以用在：
- **子代理 / 较弱模型的产出**：主会话让子代理交凭证，而不是交一段「已完成」的总结。
- **无人值守任务**：任务卡里的每条要求是一笔借方，结束前必须逐笔交凭证；门禁结果直接附在汇报里。

## 6. 历史回放怎么做

1. 选回放点：你知道答案（后来审计或事故找到的问题）之前的那个提交。答案只用来评估，不给任何子代理看。
2. `scripts/snapshot.sh` 只读导出两份快照：只含设计文档的（给规划会话）、完整的（给实现会话和复核员）。不要在原仓库 checkout。
3. 规划会话按文件分批开借方（每批几份文档、每份最多 15 笔），实现会话按借方分批交凭证。
4. `reconcile` 出试算；`orphans` 出反向清单。
5. 复核：没入账的全量裁定（`adjudicator.md`），已入账随机抽样查漏报（`fn-checker.md`）。你自己再抽查关键项。
6. 和答案对：每处已知问题，正向抓到 / 只给线索 / 反向抓到 / 漏了，各自为什么。
7. 可以再选一个更早的回放点（某次归档）看门禁能提前多久，以及一个修复后的回放点看修好之后会不会被误拦。

## 7. 成本

回放规模（60 多份设计文档、265 笔代码层借方）：规划 4 个子代理、实现 9 个、复核 3+1 个；机械核验和反向扫描都是秒级。日常用在单个 change 上，借方通常是几笔到几十笔，一个规划会话、一个实现会话就够。
