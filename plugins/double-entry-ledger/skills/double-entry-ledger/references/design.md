# 设计说明：会计概念映射、检出能力与局限

## 1. 会计概念与 harness 机制的对应

| 会计概念 | 本工具中的对应 | 作用 |
|---|---|---|
| 有借必有贷，借贷必相等 | 每条记录内同一单位的金额之和为 0，否则拒绝写入 | 杜绝单边记账和半写入 |
| 计量单位 | `unit`（count / tokens / usd / 实体 id…），**不同单位永不相抵** | tokens 与 usd 不能互相掩盖 |
| 试算平衡 | `trial` / `verify` 全量回放求和 | 兜底手改、漏行、记账代码 bug |
| 科目性质（资产不能为负） | `rules[].min/max`；`mode: reject` 拒记，`mode: flag` 照记并标红 | 同一任务完成两次被拒；预算超支照记、标红、阻止结账 |
| 原始凭证 | 探针取数（文件、JSON）、harness 签名的工具返回值 | 实际发生额来自代码，不来自模型的叙述 |
| 预算会计的承诺 / 保留（encumbrance） | `clearing:intent:<id>:<i>` | 开单时为计划占一笔，结算时用实际冲销，余额即「计划 − 实际」 |
| 挂账（暂记 suspense） | `suspense:*`，按期望 / 对账目标逐项开立，只能用 `clear-suspense --reason` 清理 | 说不清的差额先挂起：不准猜，不准悄悄调平，也不准相互抵消 |
| 银行余额调节表 | `reconcile`：账面 vs 探针 / 外部快照；`--since-close` 比较本期发生额 | 抓语义错误：账上有，现实里没有 |
| 红字冲销 | `reverse` | 不改历史，只追加更正分录 |
| 期末结账 | `close`：临时科目必须已归零；快照余额和链头哈希 | 阶段边界的硬门槛，也是审计锚点 |
| 职务分离（记账 / 审批 / 保管分开） | 模型只声明；harness 代码记账、取数、签名；人复核干预项并结账；锚点存在账外 | 防止模型自证或自改账 |
| 凭证连续编号 | `seq` 加 `prev` 哈希链 | 删行、插行、重排、改值都能被发现 |
| 会计政策变更须披露 | 每条记录带配置指纹 `cfg`，期内配置变更会被提示 | 防止改配置悄悄放宽规则 |

**符号约定**：金额带符号，正数为借（流入该科目），负数为贷（流出）。这和 ledger-cli / beancount 一致。
「计划记借、实际记贷」只是对正向变化的直观说法；负向变化（如 `-1`）的方向相反，但余额仍然等于「计划 − 实际」。

## 2. 各项检查能抓什么、不能抓什么

| 检查 | 能抓 | 抓不到 |
|---|---|---|
| 逐笔平衡（写入时） | 只记了一边、金额写错导致不平 | 两边都错但仍平衡；**记了一笔现实中没发生的事** |
| 科目规则 | 重复完成、超支、负库存 | 数值在范围内的错误 |
| 受保护科目 | 不经核实直接迁移或销毁状态，包括伪装成「新建」的迁移、先销毁再新建 | 直接把实体新建在终态池里（要靠「只创建一次」规则和外部对账来抓） |
| 人工复核清单（`verify --strict`） | 本期所有绕过核实的动作：`--direct`、核销、清挂账、对账调整、override、未签名观测 | 人看了清单但没认真复核 |
| 哈希链、seq、前缀摘要 | 意外手改、删行、截断、写到一半崩溃 | 有人重算整条链（要靠账外锚点 `verify --anchor`） |
| 试算平衡 | 绕过 `post` 直接改文件造成的不平 | 逐笔已平的前提下基本恒平。**不要把它当成语义检查** |
| 意图清账 | 把计划当结果、只完成一部分、多做了、做到别处去了 | 期望本身选错（所以用工具模板，并拒绝「必然通过」的期望） |
| 签名观测 | 模型冒充 `source=tool`、事后补写假观测覆盖真实观测 | harness 自己的取数 bug |
| 外部对账 | 账实不符：记忆写了但工具失败、外部被别人改了、漏报用量 | 对账目标没覆盖到的科目 |
| 结账 | 未结意图、未清挂账、标红项、子预算未归零（agent 失联或漏报） | 结账前没纳入规则的科目 |

**结论**：「等式不平 = 工具失败但记忆照写」只在两条腿**分开写**、中途崩溃时成立。
本工具让每笔分录原子写入，所以这种情况交给另外两层处理：
- **意图清账**：`then` 只在效果核实后过账。
- **外部对账**：直接拿账面去对照现实。

## 3. 设计决策与理由

- **清账和挂账都按期望逐条开立**（科目名带 `:<i>` 后缀）。设想计划是「done +1、todo −1」：
  - 如果实际只做了复制（done +1、todo 0），逐条开立能看出 todo 那一条没做到。
  - 如果实际什么都没做，两条放在同一科目里净额就是 +1 − 1 = 0，异常被完全掩盖。逐条开立后，每个维度单独暴露。
- **拒绝「必然通过」的期望**。预期变化全为 0（目标早已满足、`+0`）的意图默认被拒；挂了 `then` 的意图至少要有一条会真实变化的期望。
- **旧报告问题**：`json:` 期望只看数值，上次留下的旧报告同样能满足它，所以要配一条 `sha256:<报告> changed`。
- **重复结算只补记增量**；已核销或已撤销的意图不能再结算，也不能用同一个 id 重开。
- **撤销必须能证明「什么都没发生」**。结果未知（缺观测、探针失败）时一律拒绝撤销。
- **「结果未知」和「确定没做成」分开**。claim 缺观测或观测不被采信、探针执行出错时，结算状态是 `unknown`，输出标 `?`；只要有一条确定不符，就是 `mismatch`。报告文件还没生成（`json:` 目标不存在）算确定尚未产生。两者都不能报告为完成，但 `unknown` 不能当作没发生去重做。
- **`verify --strict` 与 `close` 口径一致**。除未结意图、挂账、标红、人工干预外，子预算没归零、`require_reconcile_before_close` 未满足等结账门槛也会让 strict 不通过，免得 agent 在结账前一刻才发现。
- **结账要写明复核人**。本期有人工干预或未核实项时，`close` 必须带 `--reviewed-by`，复核人和复核清单写进 close 记录，签收这件事有据可查（实测中 agent 在用户说「能结账就结账」时会自己去执行 close）。
- **时间戳带时区偏移**。`ts` 用本机时区并写明偏移（0.3.0 起；更早的记录是 UTC），人读的输出换算成本机时间。
- **then 被规则拒绝时，已核实的效果照样入账**（状态记为 `then_rejected`），只是不更新状态。这时说明账面与现实不一致，应先更正账面再重新结算；不允许把它核销成「没做成」。
- **超支照记**。资源已经消耗掉了，拒记只会让账失真。需要事前拦截时，用预留（encumbrance）模式。
- **对账差额逐目标挂账**。done +1 和 todo −1 如果进同一个挂账科目会相互抵消，模型就能借「对账调整」完成一次没有证据的迁移。
- **新建的判定很窄**：受保护行必须全部是流入，其余行必须全部是来源科目。迁移、销毁，以及混在一起的写法，都要经核实。
- **可信度在结算时判定并写进记录**（受哈希链保护）。没有密钥的一方事后也能看到「当时是否已签名核实」；签名无效则是违规。
- **逃生口必须留痕**：`--direct`、`--allow-noop`、`--allow-shared-probe`、核销、清挂账、对账调整都会进入本期复核清单。`verify --strict` 在人结账确认之前不会通过。
- **探针重叠按规范化路径判断**：消去 `.`/`..`、在大小写不敏感的文件系统上折叠大小写、glob 按静态前缀判断、父子目录算作重叠。
- **id 幂等**：内容相同的重复提交返回原记录（冲销的比较还包含冲销对象），内容不同则拒绝。
- **精确算术**：金额用 Decimal，拒绝 float；限制位数（整数 ≤ 30 位，小数 ≤ 18 位），在高精度上下文里计算，一旦发生舍入就报错。
- **默认规则不能被悄悄去掉**。用户规则追加在默认规则之后；要整体替换，必须显式设置 `replace_default_rules`。
- **探针只读，默认不能越出根目录**。配置里不支持执行任意命令，因为分发出去的 skill 可能读到别人仓库里的配置文件。
- **损坏即停**。哈希链断了就拒绝继续记账；只有「末行不完整」（那条记录从未被确认写入）会在先备份后自动截掉。
- **前向兼容**：每条记录带 `v`。遇到更高版本写入的未知记录类型，只按通用分录回放并给出提示，不判为违规。

## 4. 已知局限

1. **探针测量的是世界，不区分是谁造成的变化**。open 和 settle 之间，如果别的进程改了同一路径，变化量会被污染。工具会拒绝与未结意图共用探针，但管不到账本之外的写入者。
2. **职务分离靠部署**。签名、权限、固定配置路径都要搭建者落实（见 integration.md §0）。如果模型能读到密钥或能写 `.ledger/`，这些保护都会失效。写账本的、核账的和被核的在同一个信任边界里时，账本本身就不可信；按信任边界分的三档部署见仓库 `docs/architecture.md` §6。
3. **哈希链只防意外，不防蓄意篡改**。能写文件的人就能重算整条链；真正防篡改要靠账外锚点。
4. **清账只核对数量，不核对质量**。「写了文件」能核实，「内容正确」要交给测试，再通过 `json:` 探针接进来。也就是说，✓ 首先证明的是「操作发生了」（V1）；接上测试报告才部分覆盖「技术结果对」（V2）；「需求真的满足了」（V3）不在账本范围内。分层见仓库 `docs/architecture.md` §7。
5. **结账不会自动结转费用类科目**。`expense:*`、`intent:planned/effected` 会跨期累计。按期对账请用 `reconcile --since-close`。
6. **`then` 分录无法 `reverse`**。需要更正时，用带原因的 `post --direct`（会进复核清单）。
7. **复核清单只保证「看得见」，不保证有人看**。close 是否交给人执行，取决于部署。
8. **性能**：常驻进程增量校验；CLI 每次冷启动都要全量重放（2 万条约 0.3 s）。更大规模请按阶段换新日记账。
9. Windows 下的文件锁走 `msvcrt` 分支，未实测。
