# 架构：用复式记账给 agent 的「做完了」对账

> English summary: [README.md](../README.md#how-it-works-one-plugin-two-ledgers). 本文是完整说明。

## 1. 要解决的问题

agent 说「做完了」，有时没做完。形式有两种，时间尺度不同：

| 尺度 | 失败的样子 | 例子 |
|---|---|---|
| 会话内 | 工具说成功，效果没发生；agent 跑完命令就汇报 | `sed` 一个都没匹配上；项目脚本打印「✓ closed」其实什么也没做；构建产物写错了目录 |
| 跨会话 | 设计决策只落了一半，看起来像完成了 | 校验函数有实现、有单测，入口从没调用；决策改了，ADR 还写着旧做法；`tasks.md` 全打了 `[x]`，入口没接 |

两者的根因相同：**「做完了」是一句陈述，不是一笔可以核对的账。** 信息常常存在，散在工具输出和自由文本里，没法机械查询，也就等于不存在。

这类问题靠更强的模型、更长的提示词解决不彻底：提示词里写「改完一定要检查」，本质上还是在等模型自觉。本仓库的做法是**不信 agent 的自我汇报，另建一套由代码执行的核对**。

### 定位：执行与交付可信

这个仓库不只是「防止 AI 犯错的 Claude Code 插件」。它针对的是更一般的问题：**让 agent 的承诺可追踪、执行可核验、交付可审计**（Agent Execution & Delivery Assurance）。分三层：

| 层 | 回答的问题 | 本仓库的实现 | 现状 |
|---|---|---|---|
| 执行可信（Runtime Assurance） | 这一步做没做成 | 运行时账本：意图 → 探针 → 结算 | 有实现、有测试、有对照实验（E1、E2） |
| 交付可信（Delivery Assurance） | 这条决定落没落到代码里 | 落地账本：借方 → 凭证 → 门禁 + 反向扫描 | 有实现、有测试，只在一个仓库的历史上回放过（E3） |
| 审计与治理（Audit & Governance） | 出了问题，证据在哪、谁签的字 | 哈希链 + 账外锚点、人工复核清单、`close --reviewed-by`、门禁输出存档 | 机制有；跨团队、跨 harness 的治理流程还没做 |

Claude Code 插件只是目前的分发方式。两个核心脚本（`ledger.py`、`landing.py`）只依赖 Python 标准库，可以直接放进别的 harness 或 CI。

**现状**：这是一套有实现、有测试、有小样本实验支撑的架构原型，**还没有经过大规模真实生产验证**。实验能说明什么、不能说明什么，见 [experiments/README.md](../experiments/README.md#证据强度)。

## 2. 核心思想：复式记账

| 记账 | 本仓库 |
|---|---|
| 借方：计划 / 承诺 | 会话内：一次工具调用或一项交付的**意图**（期望效果）；跨会话：设计文档里一条代码层承诺 |
| 凭证 | 会话内：代码探针测得的实际效果；跨会话：实现方交的「定义 / 生产落点 / 测试」位置，或者自认未落地、已被取代 |
| 贷方：核验后入账 | 代码核对凭证；核对通过才入账，状态才更新 |
| 挂账 | 说不清的差额先挂起：不准猜、不准悄悄调平 |
| 对账 | 账面 vs 现实（文件、外部快照、反向扫描） |
| 结账 / 门禁 | 未结、挂账、待复核项都必须处理，才能结账（归档） |
| 职务分离 | **模型只声明；代码记账、取数、判定；人复核干预项并签收** |

最重要的一条经验（E3）：**真正起作用的是「逐笔交凭证」这个结构，不是用 grep 抓谎。** 逼着执行方对每笔承诺逐一回应，它关于自己的陈述（「这条没做」「这条被取代了」「这里和文档有出入」）精度很高；而机器靠文本匹配去判定「做没做」，精度很低。

## 3. 总体结构

```
                         ┌──────────── 设计文档（ADR / spec / tasks.md）────────────┐
                         │                                                          │
   跨会话                │  landing-ledger（落地账本）                               │
   spec → 代码           │    规划会话（只看文档）→ 借方 ── 带接线约束               │
                         │    实现会话（看代码）  → 凭证 ── 落点 | 未落地 | 已取代     │
                         │    landing.py reconcile → 门禁：阻断高精度信号，驳回进复核 │
                         │    landing.py orphans   → 反向：有定义、生产零调用         │
                         └──────────────────────────────────────────────────────────┘
                                                  ▲ 每个实现会话内部
                         ┌──────────────────────────────────────────────────────────┐
   会话内                │  double-entry-ledger（运行时账本）                         │
   工具 → 效果           │    PreToolUse  从参数推出期望，开意图（借）                 │
                         │    PostToolUse 探针测效果，结算（贷），不符当场贴给模型      │
                         │    任务意图    推不出的交付（脚本、构建、测试）由 agent 登记 │
                         │    Stop        全部重结，未兑现的给模型看一次、再给用户看   │
                         │    close       干净就结账，链头哈希写到账外               │
                         └──────────────────────────────────────────────────────────┘
```

| 组件 | 位置 | 核对什么 | 谁记账 | 门禁 |
|---|---|---|---|---|
| `ledger.py` | `skills/double-entry-ledger/scripts/` | 状态迁移、工具效果、多 agent 预算 | 代码（harness 或钩子） | `verify --strict` / `close` |
| `cc_hook.py` | 同上 | Claude Code 里的 Write/Edit/Bash 文件操作 | 钩子 | Stop 时给用户看账面结论 |
| `landing.py` | `skills/landing-ledger/scripts/` | 设计决策是否落到代码 | 代码（核验器）+ 复核员 | `reconcile` 退出码 0 / 1 / 3 |

共同的三条规则：
1. **模型只声明。** 期望、借方由规则或另一个会话给出；效果由代码测；判定由代码或独立复核员做。
2. **三态：过 / 不过 / 没查。** 没跑的检查不能显示成通过（`settle` 的 `unknown`、`reconcile` 的 `--tests not-run`、退出码 3）。
3. **逃生口留痕，人签收。** 核销、清挂账、直接过账、复核项，全部进清单，由人签收（`close --reviewed-by`、门禁的复核清单）。

## 4. 和 harness 五层的对应

| 层 | 解决什么 | 本仓库提供的 |
|---|---|---|
| L1 约束 | AI 不知道红线 | SKILL.md 的规则和「红旗」清单；钩子的守卫（不准写 `.ledger/`、不准自己结账、不准自己写观测）——守卫是把 L1 从「嘴说」变成「拦住」 |
| L2 路由 | 上下文塞太多反而更笨 | skill 的 description 决定什么时候加载（E1 实测「做记账 app」误触发后收窄）；给模型看的只有一行结论（`verify --quiet`、settle 的一行、Stop 的一句），不让它读日记账 |
| **L3 反馈** | AI 说做完了，其实没做 | **运行时账本**：每次工具调用当场结算，不符的项贴在工具结果旁边；Stop 时代码重结，结论直接给用户看。锚点 A「跳过 ≠ 通过」落实为 `unknown` 状态和「没查」 |
| **L4 判定** | 半成品伪装成完成品 | **落地账本**：设计决策逐笔开借方、逐笔交凭证；门禁拦「自认未落地 / 自述偏差 / 取代未冲销 / 没凭证」。锚点 B「半落地」从「靠人审计发现」变成「归档时就被拦下」（E3：可提前 24 天） |
| L5 反测 | 规矩写了，它到底守不守？ | 实验本身就是反测：故障注入（E1）、施压场景（E2）、对抗凭证（E3）、对抗审查（E2 §5）。`examples/demo/adversarial/` 把「借方写太松就能被骗」做成了可复现的反测用例 |

账本的位置在 **L3 和 L4 之间**：L3 回答「这一步做没做成」，L4 回答「这条决定落没落地」；两本账用同一套记账结构把两层接起来——落地账本里每张凭证背后，是实现会话里运行时账本已经核对过的一笔笔工具效果。

## 5. 什么时候开、开哪个（定位）

| 场景 | 建议 | 依据 |
|---|---|---|
| 强模型、单会话、短任务 | **都不开**。它本来就会回头核对，开了只加成本 | E1：带不带 skill 一样诚实；E2：Opus 所有条件 0 虚报，钩子 +60%～120% 成本 |
| 弱模型 / 子 agent、或者被催着「别检查」 | 开运行时账本（调用 skill 即挂上钩子） | E2：Haiku 施压虚报 7/8 → 1/10，完成数 1.38 → 2.70，+$0.005/次 |
| 无人值守任务 | 运行时账本 + 任务结束前逐笔交凭证（落地账本的轻量用法：任务卡每条要求一笔借方） | 无人复核时，「Stop 时给用户看账面结论」是唯一不经过模型总结的信号 |
| 崩溃恢复、多 agent 预算 | 运行时账本，挂在 harness 进程里（不是 skill） | E1：没有账本，哪些动作做了一半、邮件发没发、谁花了预算这些信息根本不存在 |
| 跨会话 spec → 代码（OpenSpec/SDD 归档） | 落地账本，在归档前跑门禁 | E3：5 处半落地抓 4 + 1 线索；归档时就能拦下 |
| 只给 agent 一份规则、不配钩子也不配凭证 | **不要这样做** | E2：只有规则的 v0.3.0 让交付变少、虚报没减少；E1：一句指引能让 agent 去改验收脚本 |

一句话：**账本对「会自己回头核对的强模型」没有增量；它的价值在模型不会回头看的地方（弱模型、被催、子 agent、无人值守）和人记不住的地方（跨会话的决定、崩溃留下的半截状态、多 agent 的花费）。**

## 6. 信任边界：账本本身不天然可信

账本是用来核对 agent 的。可如果写账本的、核账的和被核的都在同一个信任边界里，账本自己也可能被污染：agent 能改 `.ledger/`、能改核验脚本、能关掉钩子，哈希链就只能发现「意外」的改动。所以先说清楚它防什么：

| 防得住 | 防不住（除非按下表 T1 / T2 部署） |
|---|---|
| 模型的疏忽、偷懒、跑完命令就汇报 | 有意绕过约束的 agent：改账本、改核验脚本、关钩子、伪造观测 |
| 工具说成功但没生效（`sed` 没匹配上、`\|\| true` 吞掉错误） | 在同一环境里重算整条哈希链（只有账外锚点能发现） |
| 意外手改、截断、写到一半崩溃 | 核验器自己的 bug |

按信任边界分三档部署：

| 档位 | 谁能写账本和核验结果 | 怎么做 | 防到哪一步 |
|---|---|---|---|
| T0 同一环境（插件默认） | agent 和钩子是同一个用户、同一个环境 | 会话里调用一次 `/double-entry-ledger` | 疏忽和顺手的越权。守卫只是尽力拦截，能被绕过 |
| T1 账本保护 | 只有 harness 进程能写账本，agent 只读 | 用操作系统权限、容器只读挂载或宿主的沙箱规则，让 agent 对 `.ledger/` 没有写权限；`LEDGER_OBSERVER_KEY` 只在 harness 里；`close` 由人执行；链头哈希写到账外 | 改账本、伪造观测、自己结账。检查表见 `integration.md` §0 |
| T2 独立核验 | 核验跑在 agent 碰不到的进程或机器上，结论写到 agent 写不进的地方 | 运行时：harness 在独立进程里取数、结算，agent 只收结论。落地：把 `landing.py reconcile / orphans` 放进 CI，对只读快照跑，门禁结果作为合并或归档的前提；核验脚本固定版本（例如校验哈希） | 改核验脚本、改核验结果 |

现在代码直接提供的是 T0，以及 T1 要用到的签名观测（`LEDGER_OBSERVER_KEY`）、账外锚点（`verify --anchor`）和人工签收（`close --reviewed-by`）；隔离本身要靠部署落实。落地账本放进 CI 已经能做到 T2（脚本没有依赖，退出码就是门禁）。运行时账本的独立核验还没有现成的参考实现，列在 §10 的 P0。

方向：**把核验器、账本存储和 agent 的执行环境分开，至少让 agent 改不了核验结果。**

## 7. 核验深度：✓ 证明到哪一层

「核验通过」有不同的深度，混在一起说会高估账本的作用。为了不和 §4 的 harness 五层（L1～L5）混淆，这里记作 V1～V3：

| 深度 | 核验什么 | 例子 | 谁来证明 |
|---|---|---|---|
| V1 操作发生了 | 预期的副作用是否真的出现 | 文件变了、数量 +1、报告重新生成了 | 运行时账本的探针。这一层比较扎实 |
| V2 技术结果符合预期 | 产物在技术上对不对 | 测试通过、产物在正确的位置、决策在生产代码里有调用点 | 部分覆盖：`json:` 探针接测试报告并配 `sha256 changed`；落地账本核验落点和测试引用（静态的，限制见 §8） |
| V3 需求真的满足了 | 用户要的东西是否得到了 | 功能可用、行为符合验收标准、没有破坏别处 | 账本不覆盖。要靠测试、业务验收或独立评审 |

所以：

- 运行时账本的 ✓ 首先是 V1：「效果发生了，和计划一致」。只有把测试报告接进探针，才延伸到 V2。写入成功不代表内容符合需求、没有破坏别的逻辑、代码能正常运行。
- 落地账本的「入账」是静态意义上的 V2：定义在、生产调用点在、有测试引用。**有调用点不等于运行时一定会执行。**
- 两本账都**不证明** V3。引用账本结论时，应写成「已核对到 V1 / V2」，不要写成「需求已完成」。

## 8. 落地账本的定位：找出半落地的风险，不证明代码正确

`landing.py` 用定义、调用点、符号引用、作用域、关键字来判断一条承诺有没有落地。这有实际价值，但静态扫描有天然的上限：

- **动态调用**：`obj[name]()`、反射、按字符串注册的处理函数，扫描看不到调用关系。
- **依赖注入**：容器在运行时把实现绑定到接口上，扫描看到的是接口，看不到实现被谁用了。
- **跨模块的间接调用**：多层包装、高阶函数、事件总线可能被漏掉。回放里机械驳回的误报，大头就是「规则太死」。
- **配置驱动的接线**：路由表、插件清单、YAML / JSON 里的注册关系，代码里没有直接调用。
- **有调用点不等于会执行**：特性开关、走不到的分支、只在测试里构造的路径。

所以它的定位是：**把高风险的半落地决策找出来，交给人或独立的 agent 去审，而不是替代代码审查。** 这也是门禁只拦实现方自己的陈述（自认未落地、自述偏差、取代未冲销、没交凭证），而把机械驳回放进复核清单的原因（数据见 `method.md` §3）。

不打算把它做成一个「证明代码都对」的静态分析器。以后引入 AST 或调用图（§10 的 P2），目的是减少复核清单里的误报，不是让机器判定取代复核。

## 9. 落地路线

1. **先上落地门禁**（成本最低、收益最清楚）：在 OpenSpec change 归档前跑 `landing.py`，只阻断四类高精度信号，机械驳回进复核清单。见 `skills/landing-ledger/references/method.md` §5。
2. **给子 agent / 弱模型开运行时账本**：派子任务时让它调用 `/double-entry-ledger`；主会话收的是账面结论，不是它的总结。
3. **真正的职务分离要挂进 harness 进程**：普通 Claude Code 会话里钩子和模型的 Bash 同一个环境，守卫只拦顺手的越权。要防蓄意绕过，按 §6 的 T1 / T2 部署，检查表见 `skills/double-entry-ledger/references/integration.md` §0（observer 密钥只在 harness、模型对 `.ledger/` 无写权限、`close` 只能人执行）。
4. **补运行时计数对账**：「某个操作执行了多少次 vs 留下了多少条记录」这类只有生产数据能回答的事实，作为独立一项定期对账（`ledger.py reconcile --snapshot`）。

## 10. 已知局限与路线图

| 局限 | 影响 | 下一步 |
|---|---|---|
| 实验样本小、场景少，多数陷阱是人为设计的 | 数字只代表方向，不能外推到所有模型、任务和工作流 | 真实开源项目盲测（E4，方案见 `experiments/e4-blind-test/PLAN.md`）；长任务、多 agent 上各跑一段时间，统计不符和对账差额 |
| 机械核验靠文本匹配 | 驳回精度约 5%，只能进复核 | 换成 AST / 调用图（如 ts-morph），目的是减少复核负担；重新测精度之前不让驳回阻断（§8） |
| 门禁不防蓄意造假的凭证 | 造假只会进复核清单 | 复核清单必须真的有人看；或 `--strict` |
| 借方只能对写进文档的承诺 | 只活在注释和人脑里的承诺漏掉 | 反向扫描兜底；把「决定」写进 ADR/spec 本身就是 L4 的一部分 |
| 普通会话里守卫可被绕过 | 拦不住对抗 | 按 §6 的 T1 / T2 部署 |
| 探针只核数量不核质量 | 能核 V1，V2 要接测试报告，V3 不核（§7） | 把测试报告接进 `json:` 探针，用 `sha256 changed` 防旧报告；V3 交给验收和独立评审 |
| 钩子适配器只有 Claude Code 一种 | 换一个 agent 宿主就只剩手动 CLI | 适配更多 harness（P1） |

按优先级排的下一步：

| 优先级 | 工作 | 目的 | 现状 |
|---|---|---|---|
| P0 | 独立核验环境、账本保护：给出 T1 / T2 的参考部署（核验在独立进程，agent 对账本只读，核验结果写到 agent 写不进的地方） | 提高信任边界 | 签名观测、账外锚点、人工签收已有；参考部署没做 |
| P0 | 真实开源项目盲测（E4）：独立审查者标注，比较有无账本时的召回率、误报率、成本和完成质量 | 验证实际价值 | 方案已写，未开始 |
| P1 | 适配更多 agent harness（其他 coding agent 的钩子机制、自建 harness 的工具执行器） | 摆脱单一生态 | 只有 Claude Code 适配器；自建 harness 可以直接用 Python API |
| P1 | 可视化审计报告：把账面结论、复核清单、门禁结果导出成一页能直接看的报告 | 降低使用门槛 | 只有 CLI 文本和 `--json` |
| P2 | 支持更多语言和 AST 分析 | 减少静态扫描误判 | 文本匹配，覆盖 TS / JS / Python |
| P2 | 多 agent 统一预算和交付追踪 | 扩展治理能力 | 运行时账本有子预算归零检查；跨 agent 的交付追踪没做 |
