# E4 真实项目盲测（方案，未开始）

> 状态：**还没有跑，这里没有任何结果。** 本文是开跑前的方案；指标、判定规则和排除标准会在开跑前定稿并提交，之后不改。

## 为什么要做

E1～E3 的强度有限（见 [../README.md](../README.md#证据强度)）：E1 的故障是人为注入的，E2 只有一个场景、每组 3～10 次，E3 只有一个闭源仓库。它们能说明机制按设计工作、在设计好的陷阱上有效，但回答不了「在真实项目里到底有没有用、值不值这个成本」。继续增加人为设计的陷阱，说服力也不会提高。

## 要回答的问题

1. 运行时账本：在真实任务里，虚报完成的比例能降多少？成本（token、时间、费用）增加多少？会不会让交付变少？
2. 落地账本：对真实存在的半落地，召回率是多少？复核清单给人带来多少负担（误报）？
3. 以上结果在强模型和弱模型、短任务和长任务之间差多少。

## 设计

**选项目。** 3～5 个活跃的开源仓库，条件是：有 ADR、spec、RFC 或 tasks 这类设计文档；测试能在本地跑；历史上有能考证的「设计写了、代码后来才补上或一直没补」的提交（用作落地账本的回放答案）。至少覆盖两种语言。

**取任务。**
- 运行时：从真实 issue 和已合并的 PR 里抽任务，以 PR 合并前的提交为起点。
- 落地：在设计文档定稿、实现声称完成的提交上设回放点，答案取自之后的修复提交和讨论记录。
- 任务清单在开跑前冻结。

**实验条件。**
- 运行时：无账本 / 只有规则 / 钩子；模型至少一强一弱；每个任务 × 条件重复多次，次数按预算在开跑前定好（目标每格不少于 20 次）。
- 落地：同一回放点上，对比「落地账本门禁 + 复核清单」和「只看实现会话的完成总结」，再加一组「一个独立 agent 直接读文档和代码做审查」作为基线。

**盲标。** 由不参与实验设计、看不到实验条件的审查者标注每个交付项的实际完成情况，以及每个回放点上真实存在的半落地。可以是人，也可以是与被测模型不同家族的模型加人工抽检；标注规则开跑前写好。两位审查者独立标注一部分样本，报告一致率；分歧由第三位裁定。

**排除。** 被污染的运行（例如 E2 第 1 轮那样，agent 看到了评测线索）按事先写好的规则排除，并在报告里单独列出，不悄悄丢掉。

## 指标

| 指标 | 定义 |
|---|---|
| 虚报率 | 汇报为完成、但标注为没完成的交付项 ÷ 汇报为完成的交付项 |
| 召回率 | 账本或门禁指出的真实问题 ÷ 标注出的全部真实问题 |
| 误报率 / 复核负担 | 账本或门禁指出、但标注为没问题的项 ÷ 账本或门禁指出的全部项；以及每个任务需要人看的条数 |
| 成本 | token、墙钟时间、费用，相对无账本的增量 |
| 完成质量 | 测试通过率；独立审查者按验收标准打分（对应 `docs/architecture.md` §7 的 V3） |

## 什么结果说明「没用」

事先写下来，免得事后挑对自己有利的解读：

- 强模型上，无账本时的虚报率本来就接近 0：预期运行时账本没有增量，这和 E2 一致，不算失败，但要如实报告成本。
- 弱模型上，虚报率下降不明显，或者成本明显增加而完成质量不变：运行时账本在这个场景下不值得开。具体阈值开跑前定。
- 落地门禁的召回率不高于「独立 agent 直接审查」这个基线，或者复核负担明显更高：落地账本的结构没有带来增量。
